## 正文

目标：学会把 Luna、Terra、Sol、Astra 聪明地分开用，拉高产出、压低成本，并让代理工作流能长时间跑下去。

OpenAI 的 GPT-6 Astra 于 2026 年 9 月 3 日发布，代理做以前很依赖人的复杂电脑任务，能力上了一个台阶。但真正的问题已经不是「Astra 能不能干这个」，而是：

Astra 到底在哪创造价值？资源怎么分？怎么让代理干得更久？怎么用尽量低的成本做到这些？

本文主要写给常用 Codex 和编程代理、尤其接近生产环境的人。适合：用 Codex 或 OpenAI API 在近生产环境跑代理；想在 Luna / Terra / Sol / Astra 之间切换以降低每月 API 或基础设施账单；想建长时间工作流（彻底调试、大重构、电脑工具、数学验证、自动测试、必须长时间保住上下文的活）。

0. 先决条件：部署、企业、Daybreak 和能不能用

先确认模型对你的账号和环境真的可用。2026-09-03 官方宣布。Trusted Access / Daybreak 会是最早通道之一；Plus、Pro、Business、Enterprise 以及 API 和 AWS 随后。企业环境可能要管理员明确打开。免费档不把 Astra 当免费模型。付费计划可能有额外积分。部分高级网络安全能力可能绑在 Daybreak 这类路径上。API 模型 ID：`gpt-6-astra`。本文所列标准 API 价：输入每百万 $10，输出每百万 $50；长上下文、缓存、优先处理另有价。界面上看不到 Astra，不等于组织没有这个模型。先查可用性、权限和部署。等开通期间，策略可以先用 Sol 当底座来建。





GPT-6 Astra 发布之后，你试过了吗？ 你最不满意的是什么地方？

可能很多人跟我一样，就是额度不够，很快就用完了，即使是 Pro 用户也在所难免。

来看看视频里的这个家伙，用10 分钟教你用 GPT-6 Astra 来构建价值 50k 的网站，是不是很夸张，你来看看这效果真不摆了，该下岗的也每脾气了。

所以，我觉得我们要保证 使用 GPT-6 Astra 姿势，好钢用在刀刃上。不要什么活都交给它，有些简单、甚至重复性的活，完全没必要让它上。

也就是说 Astra 这种高端模型，我们尽量让每一个 token 都用的恰到好处，不浪费。Astra 的每个 token 明显更贵，但单价不等于完成成本。如果它更少出错、更少轮次、更少返工、更少工具调用、总时间更短、成功率更高，按「做完的任务」算可能更有竞争力，甚至更便宜。

所以那些任务比较适合使用 Astra 呢？ 电脑的操作、浏览器的使用、复杂长任务多工具链、调试链路长的、比较大的重构、以及数学科学、复杂端到端的任务等等。
另外给大家校准一下 Astra 该用哪档推理强度：GPT-6 Astra 开 low，已经强过 GPT-5.6 Sol 开 high。如果你以前用 Sol 开 high 就满意，建议 Astra 改用 low 或 medium。没必要全部都上 Ultra。真的有点浪费了。如果你实在不差钱当我没说。

最后，还是讲一下有些任务，完全没必要上 Astra。有兴趣的可以看看我文章中使用的工作流：Apodex 从开源模型提供到开源 Agent Harness，同时还提供官方的API，目前还有免费API 提供调用尝试，可以来试试这个，真的也很强。 

1. Astra 强在哪，Sol 何时够用

Astra 是面向专业活的高端模型，尤其：电脑使用、浏览、软件工程、代理、科学、数学、复杂端到端。官方把高端模型放在最难的从头到尾工作上。正确策略不是什么都用 Astra，而是：只有当更高能力真能改变结果时才用它。

差别最容易出现在：多文件或多模块、很多连续步骤、大量用工具、跟 GUI 打交道、难复现的问题、数学推理、长时间调试、出错很贵、上下文会丢、必须长时间维持同一策略。日常简单活，差别可能小得多。所以好规则是：别问哪个模型「更好」，问「正确做完这件事，哪个更便宜」。

OSWorld、Mind2Web 有用，但要会读。官方材料里 OSWorld 2.0 延迟模拟：Astra CPU 利用率高于 Sol，所示对比中每任务时间大约少 47%。例如 Astra 约 40 分钟，Sol 约 75 分钟。分数大约 Astra 72.6%、Sol 65.7%。另称 Astra + 新 Codex harness 在部分 Mind2Web 测试上大约比当前 Sol 体验快 1.9 倍。记住两件事：1）这是基准，1.9× 不等于公司内部每件事都快 1.9 倍；2）它仍是有用信号。任务越依赖屏幕、工具、导航、多步动作、中间决策，越该评估「模型 + 代理系统」，而不是只比每秒多少 token。

先用 Sol / Terra / Luna，当：一轮就能答完；只改一两文件；测试很短；主要是读；不需要 GUI；不需要复杂工具；重做成本低；失败后果不大。反过来才轮到 Astra：很多文件、很多模块、很长的工具链、电脑使用、复杂调试、数学验证、失败意味着大量返工、长会话里丢上下文。

2. ChatGPT、API、Codex 配置

Astra 可用时：Web 或桌面打开 ChatGPT，看模型选择器，选 Astra / GPT-6 Astra。用 Codex 也确认同一模型在那里。看不见就查套餐、企业权限、部署，临时用 Sol。Pro / Business / Enterprise 可能有特定变体，不要只看界面名字下结论。

API 基本就是在 Responses API 里指定模型。工具调用优先用 Responses。Astra 不支持 `reasoning.effort = "none"`。推理偏低时从小配置起，只在需要时再加。temperature、top_p 这类传统参数可能没有。欧盟数据驻留可能限制 Fast/Priority。缓存可能迁到 `prompt_cache_options.ttl`。

长会话里 Codex 的上下文管理可以超出「压缩聊天记录」。想法是保住：已查过的假设、已否定的假设、看过的文件、跑过的测试、得到的结果、做过的决定。实验性上下文管理要当实验，对照当前 Codex 版本再当成团队标准。几小时调试里丢上下文，会逼代理重新查哪些假设已否、哪些文件已看、哪些命令已通、哪些测试已跑。记笔记减少这种重复。敏感信息、密钥、API key 永远不要写进代理的持久笔记。

自动化的目标不该是「代理什么都能做」，而该是：可逆的全自动，不可逆或高风险的才加人。交互起点建议：`approval_policy = on-request`，`sandbox_mode = workspace-write`。代理可以读文件、跑测试、看日志、做本地改动、提交、准备 PR、自审、修 bug。人保住：生产、部署、最终 merge、发布、外发、改权限、不可逆操作、机密。批准应变成最后一个检查点，而不是全程打断。

重要活开始前，代理必须知道项目规则。有用的拆法：AGENTS.md = 永久规则、允许范围、约束、完成条件、必跑测试、人批准点；Skills = 重复流程、工作流、检查清单、专业工序；MCP = 外部连接、服务、工具、数据源。简单说：AGENTS.md 是规则，Skills 是程序，MCP 是连接。

3. 怎么写指令才能用上 Astra

长代理里，指令质量影响极大。Astra 对含糊、矛盾、过时指示、不一致 Skills、重复规则很敏感。一套好配置，提升可能不亚于换模型。

提高自主：别写一堆让它不断来问的句子，把「它可以自己行动的空间」写清楚。批准放在可审结果之后。最好的规则之一：先产出可审的东西，再为不可逆步骤要批准。避免「代理→问→人→代理→问→人」，换成「调查→实现→测试→准备结果→人批→最终动作」。长会话里，独立问题不该打断主任务。主任务用一句话写死完成条件；执行中冒出独立问题，简短回答且不中断；只有问题改变方向、范围、权限或必交产出时才停。API 也可以在执行中途追加指示，长工具用异步。

能并行就写明。独立调查、模块级改动、测试验证、文档检查、代码审查，优先并行。代理之间的消息要短、明确、可读。例如 A 查认证模块，B 分析测试，C 看类型，D 看文档，主代理再合并。

控制测试量。小改动不要触发巨大测试套。目标是避免一次琐碎修改引爆不必要的整库测试。长调试和电脑/浏览器任务，都用带完成条件、范围、禁止操作、必测项的模板。

4. 最大化的是价值，不是 token 数

正确问题不是「怎么把 Astra 的 token 花光」，而是「每花一美元，怎么拿到更多做完的活」。按本文价：Astra 输入 $10 / 输出 $50；Sol $4 / $20；Terra $2 / $12；Luna $0.20 / $1.20（每百万 token）。Astra 每个 token 明显更贵，但单价不等于完成成本。如果它更少出错、更少轮次、更少返工、更少工具调用、总时间更短、成功率更高，按「做完的任务」算可能更有竞争力，甚至更便宜。

习惯：先写完成条件，减少无目标探索；少中间独白，优先「状态→下一步→结果」；简单核对丢给便宜模型；稳定系统/开发者前缀，利于缓存；更贵的快速模式必须能真缩短墙钟时间。每周审计：哪些任务用了 Astra、为什么、结果、大约花费、Sol 够不够、Terra 够不够、轮次、失败、返工。写不出「必须用 Astra 是因为……」，就把这类任务降档。

5. 推荐工作流

长调试：先分类（多文件、难复现、很多工具 → Astra；简单 → Sol/Terra）→ 在 AGENTS.md 划范围 → 配模型、on-request、workspace-write，长会话可开 experimental context → 用明确完成条件开干 → 记录假设/测试/结果/文件/决定 → 独立问题不毁主任务上下文 → 交付到「可审 PR」，最终 merge 人控 → 重复问题收成 Skill。

大重构：便宜模型做调研、影响、模块、风险、计划；Astra 做真正需要更强能力的模块；子代理并行测试、类型、审查、独立模块；人看架构、公开 API、兼容、不可逆决定。

电脑使用：写清目标屏幕和禁止操作；又长又视觉复杂再用 Astra；该用最新 Codex harness 就用；记录状态和步骤；变成可审交付。Mind2Web 的 1.9× 只当基准，不当内部保证。

基于 API 的代理：模型 gpt-6-astra，Responses API，推理从低到需要时再高，工具打开，长工具异步，人闸门放在最终不可逆动作。难度中途变了：真变难再加推理，常规执行回到更低档。把最贵的资源留给真正需要的时刻。

6. 做与不做

做：把 Astra 留给真能拉开差距的活；审查 AGENTS.md 和 Skills 的不一致；批准当最后检查点；先有可审结果再要授权；长活按需开上下文管理；记录假设、测试、结果；基准当方向不当内部 KPI；量成功率和每任务时间；一开始就查要不要 Daybreak；机密不进持久笔记。

不做：每个小问题都用 Astra；把宣传句当技术规格；把 X 或 Reddit 的个人体验当官方文档；管理员还没开就宣布企业已部署；自动放行不可逆操作；把秘密写进上下文文件；琐碎改动跑巨大测试；用外部基准代替内部指标。

7. 60 分钟落地

0–5 分：查选择器、API、Codex 里有没有 gpt-6-astra；企业查管理员权限。5–15：配模型、on-request、workspace-write，实验上下文需要就开，必要时重启 Codex。15–25：更新 AGENTS.md（范围、约束、测试、完成条件、批准点）。25–35：做一张 Luna→Terra→Sol→Astra 路由表。35–55：用 Astra 跑一个范围有限的真实调试，完成条件写死。55–60：记录 Astra 是否真必要、Sol 够不够、避免了多少返工、哪套配置有效、什么该变成 Skill。不必把新功能全试一遍。分配 + 边界 + 长会话 = 用好 Astra 的底座。

8–17 章压缩：两级火箭（便宜模型调研 → 必要时 Astra 执行）；第一句就写「任务完成的标志是……」；长活靠笔记，不只靠压缩记忆；批准是最后一步；KPI 用内部成功率、时间、每任务成本、轮次、返工、人介入。常见错是先骂「Astra 弱」，正确顺序是查：看得见吗、框架新不新、提示清不清、AGENTS.md 有没有打架、Skills 旧不旧、路由对不对。很多时候问题不是模型能力，是它工作的环境。

团队清单：谁用 Astra、管理员权限、负责人与截止日期、路由表、最小 AGENTS.md、approval、sandbox、人介入点、机密操作文档、每周成本回顾、哪些活真需要 Astra、重复错误收成 Skill。优先减少团队错误和返工，而不是只加速单个代理。

决策树：一轮能完 → Luna/Terra/Sol；要 GUI、工具或很多步 → Astra；失败很贵 → Astra；难度会中途变 → 考虑 Astra + 动态推理；还没有 Astra → 同一工作流先用 Sol，模型来了只换模型、保住结构。

API 迁移顺序：换模型 → 有工具就用 Responses → 检查 reasoning（无 none，够用就从低档起）→ 删模型不再支持的 temperature/top_p → 缓存迁到 prompt_cache_options.ttl → 查数据驻留 → 动态调推理 → 长工具异步。

「最大利用」在本文里不是花最多 token，而是：把 Astra 集中在真能拉开差距的任务上，其余便宜跑，并用指令、边界、批准、上下文管理，让长任务不必被无谓打断。每周更新路由表，好过任意换模型；一次真实调试，好过把新功能全点一遍；量成功率和时间，好过追基准。Astra 不可用时，Sol 可以当临时替身。

三个根本交付：动态分配表（何时 Luna/Terra/Sol/Astra）；AGENTS.md；带角色、目标、完成条件、步骤、边界、工具、验证、输出格式的长操作提示。每场重要会话开头用一张分类卡。短活很在乎每 token 价；长活更在乎做完的成本。最终度量应是：成本 × 成功率 × 时间 × 人介入，而不只是 $/1M token。

结论：Astra 的目标不该是默认干一切，而该是让每个模型干它最有效的活。Luna 走量和简单；Terra 平衡；Sol 常规和一般编程；Astra 复杂、长、代理、GUI、数学、调试、失败很贵的活。最强模式：便宜调研 → 计划 → 需要时用 Astra 执行 → 验证 → 准备可审结果 → 人只在最后检查点出现。真正的优化不是更多地用 Astra，而是确切知道何时 Astra 值得。代理越复杂，周围的基础设施越重要：AGENTS.md、Skills、沙箱、批准、上下文、路由、每任务成本。那才是从「用用 Astra」走到「为代理真正优化过的工作流」。
