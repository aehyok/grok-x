## 正文

DeepSeek Harness（dsh）一个月内 GitHub 破 20.5 万 star。作者重点拆了 Agent Loop、工具执行前策略（pre-execute）和沙箱。

核心拆法：Loop 本身尽量小，周围行为全做成插件。模型适配管流式，工具注册表管执行，session store 记可持久事实，sandbox 管文件策略，客户端只投影这些记录。

技术底座是 Cordis：共享上下文、类型化事件、可逆 effect。`@deepseek-ai/dsh-agent-loop` 通过 `ctx.agents` 注册，模型走 `ctx.llm`，工具走 `ctx.tools`，append-only session 走 `ctx.sessions`。应用从一个 named profile 启动，bundle + patch 拼成一棵 Cordis 树。

Loop 的具体驱动是 `ReactLoopAgent`。`turn()` 打开持久 turn，step 循环领取排队 prompt，发 `agent/pre-step`。允许后：追加用户消息、渲染 scoped system prompt、从 `ctx.tools` 收集 schema、从 `ctx.sessions` 派生历史。工具可并行（有上限），exclusive 调用当排序屏障。取消流会保留已输出文本并标记 interrupted；未开始的工具记 `ABORTED_BEFORE_DISPATCH`。

工具管线：`tools/pre-execute` 给出 allow / deny / ask。guard 是单调的，一旦 deny 不能被后面救回。参数在策略前快照冻结，pre-execute 不能改参数。沙箱模式随每次调用走：`read-only`（默认失败安全）、`workspace-write`、`danger-full-access`。无法强制执行请求模式时 fail-closed：`SANDBOX_UNAVAILABLE`。

作者还没深挖 subagent 委派，计划后面做。

## 原文

tl;dr: DeepSeek Harness (dsh) reached 205K+ stars on GitHub within one month, and I was curious to understand how it works, especially the pre-execution tool policy and sandbox execution, since this is something I am currently working on. Alright, let's begin with the Agent loop first.

An Agent loop looks simple on a whiteboard. Send messages to a model, execute any requested tools, append the results, and repeat. That description leaves out most of the engineering work required to make the loop safe, observable, configurable, and recoverable.
DeepSeek Harness keeps that loop small and builds the surrounding behavior as plugins. I find this separation useful because it gives each concern a clear owner: model adapters handle streaming, the tool registry controls execution, the session store records durable facts, sandbox providers enforce file policy, and clients project those records into useful views.

The high-level architecture
DeepSeek Harness runs on Cordis, the plugin framework that provides its shared context, typed events, and reversible effects. The concrete driver in `@deepseek-ai/dsh-agent-loop` registers through `ctx.agents`, model providers implement `ctx.llm`, and `@deepseek-ai/dsh-tools` owns `ctx.tools`. The append-only session store lives behind `ctx.sessions`, while prompt, sandbox, projection, and client packages contribute their behavior as neighboring plugins. A shipped application starts from a named `dsh` profile, whose bundles and patches assemble these packages into one Cordis tree.

A profile selects bundles and configuration patches for an application such as the Web client, headless runner, or SDK server. Registrations are effects, so unloading a plugin also removes its services and listeners.

Profiles and bundles solve different problems. A bundle distributes a group of Cordis configuration rows, while a profile decides which bundles are stacked for one application. DeepSeek Harness applies bundle layers first, followed by profile, home-level, and command-line patch layers. This lets an operator replace the configuration of a specific plugin row without creating another application entry point.

This model lets a timeout policy wrap execution, a client add a Trajectory view, or another loop implement the public Agent interface without modifying neighboring components.

The shared Cordis context ties the pieces together through explicit services. The loop calls the model through `ctx.llm`, dispatches tools through `ctx.tools`, and records work through `ctx.sessions`. Plugins listen to typed events when they need to influence behavior. Each registration returns a disposer, so the plugin that creates a contribution also owns its cleanup.

The Agent loop stays deliberately small
The concrete driver is ReactLoopAgent in `packages/core/agent-loop/src/agent.ts`, registered as the default factory behind `ctx.agents`. Its `turn()` method opens a durable turn, and its step loop claims queued prompts plus next-step input before emitting `agent/pre-step`. For an accepted step, it appends user messages, renders the scoped system prompt, collects tool schemas from `ctx.tools`, and derives prior messages from `ctx.sessions`.

Model chunks, the assembled assistant message, tool calls, and tool results are appended as typed session events. The loop repeats only when the response requests more tool work or a plugin supplies more step input.

If the response contains tool calls, the loop schedules them and appends their results. Parallel-safe calls can overlap within a configured limit, while exclusive calls become ordering barriers. The next step derives input from the new events. The turn closes after a final model response, cancellation, an explicit plugin decision, or an error.

The loop records turn and step boundaries, assistant chunks, assembled messages, and tool activity. It appends `step/end` from a `finally` block, giving projections a dependable record of every entered step, including failed and cancelled work.

Streaming and cancellation have explicit outcomes. A successful stream becomes one assembled `assistant/message` that cites its chunk records. A cancelled stream preserves the text already delivered to the user and marks the message as interrupted. If cancellation prevents a model-requested tool from starting, the loop records an `ABORTED_BEFORE_DISPATCH` result, so replay does not leave an unexplained tool call in history.

Tool execution in Deepseek Harness

The `tools/pre-execute` produces an allow, deny, or ask decision. Ask enters the approval service. Registered guards run next and are monotonic: once a guard denies a call, later guards cannot restore permission.

Visibility is resolved before execution for the calling agent. A plugin can register a global tool, shadow it in one agent scope, or apply allow and deny masks with `ctx.tools.restrict()`. Hidden tools disappear from that agent's model-facing schema set as well as its callable set, which keeps prompt guidance and runtime behavior aligned.

Allowed calls enter `tools/execute`, whose listeners wrap dispatch with behavior such as cooperative timeouts, retries, or measurements. `tools/post-execute` can inspect or replace a result, block it with corrective feedback, or attach context for the next step. The definition finalizes model-facing content, and `tools/result` observes the frozen outcome.

The registry also protects the identity of a call. It snapshots and freezes JSON arguments before policy runs, assigns an opaque correlation token, and validates arguments against the registered schema. Pre-execution policy cannot rewrite arguments because the recorded call, rendered UI, and executed input must describe the same action.

Everything the model sees can be reconstructed
DeepSeek Harness treats model-visible data as durable session data. A session is an append-only sequence of typed events. Its derived surface selects the messages, tool activity, and injected context that belong in later requests.

Append-only storage does not mean every event remains in the model context forever. A surface operation can replace older derived entries during compaction while leaving their raw records intact for inspection. The next request reads the current derived surface, while Trajectory and recovery logic can still reason about the underlying event history.

The Web client's Trajectory view consumes the same events. It presents turns, steps, user and assistant records, nested tool activity, tokens, timing, inputs, outputs, and durable images. Selecting a record opens its inspector, while the timeline shows where model and tool work spent time. Since Trajectory projects recorded facts, it needs no second instrumentation path inside the loop.

The loop records a canonical request header when a request series starts or its configuration changes. The header contains the resolved call configuration, rendered system prompt, and assembled tool schemas. Combined with derived history, it makes the request reconstructable from the log.

Long sessions are handled as a paged ledger. The view starts near the current tail, loads older history on demand, and virtualizes rows so the browser mounts only the visible window. This is useful during debugging because a developer can inspect one tool result in detail without forcing the whole transcript into the DOM.

The execution trace explains where time and tokens went
The compact line below the Web conversation can look like a simple counter.

Each number has a defined source. Turns and steps come from closed steps. LLM time spans `step/start` to the assembled assistant message. Tool time pairs `tool/call` with `tool/result`. TTFT uses the first non-empty stream delta, and output speed divides provider-reported output tokens by decode time.

NOTE: These figures fold over the complete durable log, so paging and compaction do not change the totals. Cache-hit and token totals come from a separate token-usage projection. The UI only renders the results.

Sandbox policy travels with each call
DeepSeek Harness centralizes file-effect policy so bash, filesystem, and terminal capabilities resolve the same session mode: `read-only`, `workspace-write`, or `danger-full-access`. The fail-safe default is `read-only`; `workspace-write` permits changes under the workspace and selected temporary areas.

Resolution follows an explicit order. A one-call approved mode wins first, followed by the session's latest logged `sandbox/mode`, followed by the deployment default. The workspace root comes from the session's immutable working directory when available. A runtime mode switch is itself a session event, so it survives restart and cannot leak into another session.

Policy travels with each confined call, allowing concurrent sessions to use different modes. An approved escalation creates one new call with a strictly wider policy. If no backend can enforce the requested mode, execution fails closed with `SANDBOX_UNAVAILABLE`.

The model receives the effective file policy in its current runtime-context snapshot before it acts. Under `workspace-write`, that message names the canonical workspace. Tool-specific denial output can then explain the blocked operation and, when approval is available, tell the model how to retry the exact call with the narrowest wider mode and a user-facing justification.

Subagent delegation is next
Everything above describes one Agent running one loop. DeepSeek Harness also ships a subagent capability that lets one Agent spawn and delegate to another, with its own session, tool policy, and sandbox mode, while the parent tracks the delegation as ordinary session events. That path isn't something I've exercised deeply yet. I'll be experimenting with subagent delegation over the coming days.
It's been fun so far....
