# 我把 WorkBuddy 的美团能力「借」给了 Codex 和 Hermes

WorkBuddy 每天签到只有 100 积分。 本期方法论提示词在文章结尾。

> btw，我发现 WorkBuddy 成长计划建议先点进去一下，后面随便用用就能有积分可以领，或者特意做任务。不过这个看个人需求，同时现阶段Hy3是限免的，如果用Hy3倒也不消耗积分。

如果让 WorkBuddy 自己每天跑一次美团自动领券，积分会继续被消耗。领券本身又是一个很小、很固定的任务，用掉这些积分多少有点可惜。

所以我做了一次很轻量的本地能力借用。

> WorkBuddy 美团生活助手
> ├─ 借给 Codex：每天 10:45 自动领券
> └─ 借给 Hermes：在微信里查餐厅、做推荐

这里的“借”非常重要。

Codex 和 Hermes 都没有独立接入美团。真正的能力来自 WorkBuddy 与美团的专项合作，我只是让自己电脑里的另外两个 AI 助手，在限定权限下调用它。

## 先说清楚：这项能力来自哪里？

美团生活助手是美团与 WorkBuddy 的 B2B 专项合作能力。

从业务结构看，它属于双方打通的 CPS/AI 渠道：美团为 WorkBuddy 配置了专属 AI 场景，WorkBuddy 用户还可以领取专享券包。

公开报道也提到，美团为 WorkBuddy 用户准备了面额更优的专属券，并支持找团购、领券和定时领取。相关合作报道

这套能力并不是面向普通开发者公开下载的美团 CLI。

所以，如果没有安装 WorkBuddy、没有添加并真正使用过“美团生活助手”，本文的方法暂时无法复现。

更准确的关系是：

> 美团与 WorkBuddy 打通能力
> → WorkBuddy 在本机安装美团生活助手
> → Codex 和 Hermes 借用这项本地能力

合作中的渠道参数、场景配置、认证信息和账号凭证都不应公开。

## CLI 到底是什么？

WorkBuddy 里的美团生活助手，表面上是一个可以对话的 AI 专家。

拆开后主要是两部分：

> 操作说明：告诉 AI 什么时候调用什么能力
> 本地 CLI：真正执行登录、领券、定位和搜索

CLI 可以理解为一组电脑终端命令。

WorkBuddy 官方文档也将 Skill 描述为“可执行脚本与工作流”，并把 `Skill + CLI` 列为连接第三方服务的一种技术形式。WorkBuddy Skill 文档

我没有复制美团接口，也没有重新开发一套服务。

我只是让 Codex 和 Hermes 调用这台电脑上已经存在的 WorkBuddy CLI。

## 为什么强调“本地能力借用”？

这次改造只发生在同一位用户、同一台电脑里：

- 不抓包；
- 不逆向美团 App；
- 不爬取美团网页；
- 不绕过登录；
- 不复制或公开 Token；
- 不重新发布 WorkBuddy 插件；
- 不提供给其他用户或账号使用。
登录凭证仍然留在 WorkBuddy 原来的本地凭证区。

Codex 和 Hermes 只能知道“当前是否已经登录”，不会读取或显示真实 Token、Cookie 和设备凭证。

因此，这项实践的边界应该明确写成：

> “仅做个人本机编排，不代表获得公开 API 或对外分发授权”。

把 Skill 文件单独复制给别人也没有用。没有 WorkBuddy 原始插件、专项场景配置和本机登录状态，Skill 只是一份操作说明。

## 基于 WorkBuddy 的美团能力，我制作了两套 Skill

两套 Skill 的权限不同：

| 步骤 | 要解决的问题 | 这次怎么做 |
|---|---|---|
| 1. 确认来源 | 原能力属于谁，现在能否正常使用？ | 先在 WorkBuddy 中确认美团生活助手已经安装、登录并可用 |
| 2. 本地转接 | 能否让另一个 AI 调用，而不复制上游能力？ | 保留 WorkBuddy 原插件，只让 Codex 和 Hermes 调用本机已有 CLI |
| 3. 安全适配 | 如何避免凭证泄露和越权调用？ | 在中间加一层适配器，隐藏 Token、限制命令并关闭自动支付 |
| 4. 权限拆分 | 不同入口真的需要相同权限吗？ | Codex 自动任务只领券，Hermes 只查餐厅，手动会话再单独授权 |
| 5. 手测后自动化 | 怎样避免把偶然成功变成每天自动报错？ | 先检查环境、演练、手动实跑，确认稳定后再创建 10:45 定时任务 |

为什么不让它们共用一套？

因为 Codex 的自动任务非常确定：

> 每天 10:45，只领一次券。

而 Hermes 长期待在微信里，收到的通常是模糊自然语言：

- “这个好像不错。”
- “附近有什么吃的？”
- “明天去湖滨银泰附近，推荐一下。”
- “帮我看看哪家划算。”
这些表达并不等于授权领券或下单。

与其只靠提示词提醒 Hermes 小心，不如直接从代码层拿掉这些权限。

## 第一套用法：Codex 每天自动领券

Codex 版本由两部分组成：

> Codex Skill
> ＋
> 美团安全适配器

安全适配器负责：

- 调用 WorkBuddy 美团 CLI；
- 检查上游版本和文件指纹；
- 隐藏 Token、Cookie 和设备信息；
- 关闭 AI 自动支付；
- 限制自动任务只能调用领券命令。
正式设置自动化前，我先手动完成三次检查：

> 检查本地环境
> → 演练领券但不实际执行
> → 手动完成一次真实领券

确认能稳定返回优惠券后，才创建每天 10:45 的自动任务。

任务还遵守三条规则：

- 今天已经领过，也按成功处理；
- 登录过期后停止重试，提醒我手动登录；
- 不得搜索位置、创建订单或发起支付。
🎟️ 实际执行过程是：

> 每天 10:45 唤醒 Codex
> → 调用 WorkBuddy 本地领券能力
> → 整理领取数量和券种
> → 用表格汇报满减与有效期

一次测试中，Codex 返回了 33 张优惠券。

但这件事不是什么“薅接口黑科技”。

优惠本来就是 WorkBuddy 与美团合作后提供给符合条件用户的。Codex 没有创造额外权益，只是把固定的领券任务从 WorkBuddy 自动化中移了出来。

它解决的是一个很小的问题：

> 少消耗一点 WorkBuddy 积分。

## 第二套用法：在微信里让 Hermes 帮我选餐厅

Hermes 拿到的是只读版 Skill。

它只允许：

- 根据用户提供的地址定位；
- 搜索餐厅和团购套餐；
- 获取距离、评分和参考价格；
- 根据人数、预算、口味进行比较；
- 最后给出一个明确推荐。
领券、下单、支付、登录和修改账户都被代码拦截。

例如可以在微信里直接问：

> 今晚去杭州湖滨银泰 in77，两个人，预算 150 元，想吃杭帮菜。

或者：

> 周末去深圳万象天地，三个人，预算 300 元，帮我挑几家适合聊天的餐厅。

🍽️ Hermes 会先利用 WorkBuddy 的美团能力筛选信息，再返回 3—4 家具体餐厅。

它不会把坐标、门店 ID、商品 ID 和原始数据发到微信里。

## 为什么手机里的 Hermes 不继续领券和下单？

这不只是安全判断，也和实际效率有关。

Hermes 在微信里收到指令后，需要把任务交给电脑终端执行，再等待结果返回手机。

如果继续领券、创建订单，还需要再次确认商品、数量和金额，最后回到手机完成支付。

在这种场景里：

> Hermes 帮忙筛选信息、比较餐厅
> → 用户选定一家
> → 打开美团 App 继续领券或下单

很多时候反而更快。

美团 App 也更适合查看：

- 实时营业状态；
- 排队情况；
- 套餐使用规则；
- 预约限制；
- 最终价格；
- 支付和退款说明。
因此，Hermes 最适合承担的是“帮我缩小选择范围”，而不是把手机消费流程全部搬到电脑终端。

AI 负责筛选，最后一步留在美团 App，体验更直接，也更稳妥。

## 谁可以复现？

## 已经在 WorkBuddy 用过美团生活助手

可以继续尝试：

> 先确认 WorkBuddy 原功能可用
> → 让 Codex 检查本地 CLI
> → 制作 Codex 领券 Skill
> → 手动测试后创建每日任务
> → 制作 Hermes 只读推荐 Skill
> → 验证危险命令全部被拦截

## 从未安装或使用过美团生活助手

先不要继续。

不要让 Codex 自己寻找隐藏接口，也不要从别人的电脑复制插件和登录凭证。

先下载 WorkBuddy，在专家页面确认自己的账号能否添加并使用“美团生活助手”。

没有 WorkBuddy 提供的原始能力，Codex 和 Hermes 都无法独立查询美团。

## 最后，该感谢的是 WorkBuddy 和美团

这项能力不是 Codex 或 Hermes 创造的。

真正把路修通的是 WorkBuddy 与美团的专项合作：

- 美团提供本地生活数据和优惠能力；
- WorkBuddy 把它包装成可被 AI 调用的美团生活助手；
- 我再基于这项本地能力制作两套 Skill；
- Codex 负责定时领券；
- Hermes 负责在微信里帮我选餐厅。
所以更准确的表达不是：

> 我给 Codex 和 Hermes 接入了美团。

而是：

> 我把 WorkBuddy 的美团能力借给了 Codex 和 Hermes。

这次改造没有产生新的美团能力。

它只是让已经存在于自己电脑里的能力，出现在更合适的时间和入口：

> Codex 帮我省一点 WorkBuddy 积分，Hermes 帮我少纠结一会儿今晚吃什么。

## 附录一：一套可以复用的“本地能力借用五步法”

这次实践真正可以复用的，不是某个文件路径或某条命令，而是下面这套顺序：

> 确认来源 → 本地转接 → 安全适配 → 权限拆分 → 手测后自动化

[link](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Skills-Market)
它背后的原则很简单：

> 能力留在原来的工具里，只把必要入口借给新的 AI 助手。

这套方法不只适用于美团。只要某项能力已经在自己的电脑上获得授权并可正常使用，同时存在稳定的本地调用入口，就可以按同样顺序评估是否值得借给其他 AI。

但“可以调用”不等于“可以随意复制”。账号权限、凭证、专属配置和分发范围，仍然以原服务的授权边界为准。

## 附录二：把这套方法交给 Codex 的提示词

⚠️如果 Codex 无法直接读取 X 文章链接，就把本文全文一并粘贴给它，不要让它根据标题猜测内容。

| 使用入口 | 允许做什么 | 明确禁止什么 |
|---|---|---|
| Codex 每日任务 | 每天执行一次领券 | 搜位置、下单、支付 |
| Codex 手动会话 | 登录、查券、搜索；确认后才能下单 | 未确认订单、自动付款 |
| 微信 Hermes | 定位、搜索餐厅、比较套餐、给出推荐 | 领券、下单、支付、登录、修改账户 |
