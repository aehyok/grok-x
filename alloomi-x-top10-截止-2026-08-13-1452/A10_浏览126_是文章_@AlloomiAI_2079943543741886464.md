## 正文

Editor’s note: This article was submitted by an OpenLoomi user and edited for clarity and readability.
As an engineering lead, I spend most of the day moving between product requirements, technical designs, and unexpected problems.
Then the day ends, and I still need to figure out what happened:
What did the team ship? Which projects moved forward? What new issues appeared? Which pull requests are waiting for me?
The answers are all there—in GitHub, Linear, email, RFCs, and notes.
The problem is that they are rarely in one place.
None of this work is difficult. It is fragmented, repetitive, and easy to postpone.
That’s how engineering updates get skipped, GitHub issues fail to make it into Linear, and PRs sit unnoticed for a day or two.
I started using OpenLoomi because I wanted to change that. Not by adding another chatbot to check, but by having something watch the workflow itself.
The first thing I stopped doing manually
Writing a daily engineering update used to mean reconstructing the day from GitHub.
I would review commits, connect them to features, identify affected modules, look for unfinished work or risk, and turn the result into a report someone else could understand.
On a busy day, I postponed it. After a few days, I was reconstructing the past from commit history, messages, and memory.
The technical judgment wasn’t the bottleneck. Collecting and reorganizing the information was.
So I set up a daily sync. Every night at 10 PM, it pulls the day’s commits and produces a structured report:
• What the team worked on
• Which modules changed
• What risks appeared
• What still needs follow-up
The report is sent to the team by email, alongside an issue synchronization summary.
The next morning starts with a consistent record of the previous day instead of another round of reconstruction.
Then I fixed the gap between GitHub and Linear
We use GitHub for code and technical issues, and Linear for planning and prioritization.
The split is useful, but the handoff is fragile.
Copying a GitHub issue into Linear often means copying only the title and description. The links to commits and PRs, discussion in the comments, reproduction details, project context, and priority are easily lost.
The Linear task exists, but it is only a shell. The next person still has to return to GitHub and rebuild the context.
I added an hourly issue sync. It checks for new GitHub issues, gathers the relevant context, and then creates or updates the matching Linear task.
The source URL acts as the identifier. If the task already exists, it is updated rather than duplicated. Repository-specific field mappings can override the defaults.
Now an issue reaches Linear ready to be prioritized and assigned—not waiting for someone to complete the migration by hand.
PR review needed a different approach
Pull requests were not a scheduling problem. They were an interruption problem.
If I checked GitHub constantly, I broke focused work. If I didn’t, an important PR could sit unnoticed.
And discovering the PR was only the beginning. Before reviewing it, I still had to gather the code summary, CI status, related requirements, risky files, test coverage, and previous discussion.
So I made PR review event-driven.
The system reaches out when a PR is assigned to me, when I’m mentioned, or when an important CI check fails. It prepares a decision card with the CI results, code summary, possible risks, and draft comments.
Nothing is posted automatically. I can approve the draft, edit it, defer the review, or skip it.
If the analysis is off, I can say:
“Remove comment 3, shorten comment 1, and focus on the potential concurrency issue.”
The draft is regenerated, and I confirm again.
The system does the repetitive preparation; I keep the technical judgment.
I thought I was automating tasks. I was really rebuilding context.
At first, this looked like three small automations: a daily report, an issue sync, and PR preparation.
But the deeper problem wasn’t the absence of scripts. It was the way engineering context was distributed:
• Code and PRs in GitHub
• Planning in Linear
• Notifications and reports in email
• Technical decisions in RFCs
• Experience and personal judgment in notes
I was acting as the integration layer between all of them.
The workflow changes that relationship.
Instead of searching across systems and assembling the current state manually, I let the system observe changes and bring me the relevant context at the moment it becomes useful.
Routine progress becomes a daily report. A new issue becomes an enriched Linear task. A PR that needs judgment arrives with the initial preparation already done.
Scheduled jobs handle stable, repetitive work. Events handle changes that need attention.
Together, the loop looks like this:
Observe → understand → assemble context → propose an action → ask for confirmation → execute and record
The result
Daily reports now appear automatically.
New issues are enriched and synchronized every hour.
Existing Linear tasks are updated instead of duplicated.
PRs reach me when a decision is needed, with CI results, risks, and draft comments prepared in advance.
Every action remains traceable.
This saves more than an hour or two each week. But the larger benefit is mental: I spend less attention switching tools, checking notifications, and wondering what I missed.
I used to think an AI engineering assistant was a better way to ask questions about a project.
Now I think that framing is too narrow.
If I still have to open a chat window, ask the right question, and provide the context every time, I am still responsible for noticing that something needs to happen.
What I need is a system that follows the work itself: one that notices change, assembles the relevant context, handles low-risk repetition, and gives control back to me when experience and judgment matter.
For me, that is the difference between an AI chatbot and an AI teammate.
