Nex-N2.5 Mini 实测：35B 开放权重，与同尺寸对照打平，文档识别只花了对方十分之一的 token
这次测的是 Nex-N2.5 Mini（35B 总参 / 约 3B 激活）：Pro（397B）权重尚未公开，Max（1.6T，纯文本）官方建议 16×H200，Nex-N2.5 三档里只有 Mini 是开放权重、能被第三方复现的那一档。 这不是退而求其次：正因为权重开放，下文每一个数字，读者都可以自己跑一遍。
先看厂方在 Creator Brief 里给 Mini 标的一行很容易被略过的数字（官方公布，非本文实测）：

一个 35B 的模型，在文档内容识别上报出了高于 397B 的 Qwen3.5 和 428B 的 Minimax-M3 的分数，距离自家 397B 的 Pro 只差 1.4。这个数字要么是真的，要么经不起复现。本文就是去复现它的，顺带把看图写页面、可交互页面、终端 Agent 和部署过程一起跑了一遍。
对照怎么做才算公平
对照模型选 Qwen3.5-35B-A3B：它与 Nex-N2.5 Mini 架构类完全相同（Qwen3_5MoeForConditionalGeneration，40 层 / 256 专家 / 激活 8 + 共享专家），尺寸相同，也正是厂方自己对比表里用的同尺寸参照。
两边的条件逐项对齐：
权重：都取 HuggingFace 上的官方 BF16 权重。Mini 的 16 个分片、共 28 个文件，逐个按 CDN 声明的字节数校验后使用。
转换：同一个 convert_hf_to_gguf.py，同样的 --outtype f16 --no-mtp。F16 只是格式转换，没有做任何量化。
运行时：同一个自行编译的 llama.cpp 构建（434ddbb，CUDA 12.4，sm_80）。
硬件：同型号同数量的卡，NVIDIA A800-SXM4-80GB × 2，权重跨两卡切分。这也是厂方对 Mini 的推荐配置。
服务端参数：-ngl 999 -c 32768 -fa on --jinja --temp 0.7 --top-p 0.95 --top-k 40 --seed 42 --image-min-tokens 1024，两个模型完全一致，随机种子固定。
题目与判分：同一批题目、同一段提示词、同一份判分代码。
重判口径：判分器修正后，是离线重判两个模型已保存的产物，没有只让其中一边重新生成。
还有一条前提要先摆出来。单独用 llama-bench -p 512 -n 128 -r 2 -fa 1 -ngl 999 测原始吞吐，跑的时候机器上没有别的负载：

两者在误差范围内完全一致。同架构、同尺寸、同样的两张卡，本来就该如此。所以下文所有耗时差异，都来自两个模型各自选择输出多少 token，不是谁跑得更快。
一、文档内容识别：都是满分，token 差了十倍
这一组对准的是官方公布的 OmniDoc 92.2。40 题、10 份文档、两个难度档。题目由脚本生成，真值来自生成过程而非人工转写，逐字段判分。第一档是财务表格取数与合计、结算单字段与行金额、双栏论文的阅读顺序与脚注、课表单元格定位与计数、表单勾选框状态。第二档是密集小字表格的行列交叉与跨行求和、带噪点与旋转的扫描小票、只能从图上读数的柱线图、划改后需按修订值作答的表单，以及阅读顺序设了陷阱的多栏简报。这一组两边都用模板默认配置。

准确率打平，两边都是满分。这说明两件事。第一，厂方 92.2 那个档次的难度，Mini 在扫描噪点、划改表单、图表读数、密集表格行列交叉这些题上确实扛住了。第二，这套题有天花板效应：对照模型也满分，所以本次复现不了官方表里 Mini 与 Qwen3.5 之间的分差，只能说 Mini 达到了那个水平。
真正拉开的是输出量。题目要求「只回答值本身」，Mini 照做，40 题总共输出 910 个 token；对照模型仍在解释，输出 9032 个。耗时 109 秒对 340 秒，差的就是这些 token。
二、看图复现开发：正确配置下打平，token 明显更少
这一组对应官方公布的 Vision2Web 48.2 这个方向，判分口径不同，分数不能直接比。4 张网页截图（定价页、运行看板、注册页、博客列表），模型只看到 PNG，要求输出单文件 HTML。判分在真实浏览器里跑：可见文字、元素数量、输入框类型、布局方向、强调色的色相，共 40 项。参考页自身先通过全部 40 项。

一个参数决定成败
博客页那一题，同一个模型、同一张截图、同一段提示词，只改一个参数：

这不是能力问题，是配置问题，但不知道的人会以为是能力问题。调用时在请求体里加 "chat_template_kwargs": {"reasoning_effort": "none"} 即可，另外还接受 high。

短回答时默认配置没有问题，文档识别那一组就是默认配置跑出来的。它出问题的地方是长生成：思考停不下来，产物写不完。
三、可交互页面：打平，但开关要按任务选
三题：Flappy Bird、Three.js 3D 页、可交互看板。生成后在浏览器里真的运行：间隔抓两帧比对判断有没有动，再按空格、拖拽、点按钮驱动一次，看画面是否随之改变，并检查有无 JS 报错。

默认配置下又是同一件事：Flappy Bird 思考了 76416 个字符，撞上 token 上限，HTML 在中途被截断，只拿到 3/9，整组 23/29。对照模型那一组是 29/29。
关掉扩展思考后，Mini 25/29，对照 26/29。这 1 分说明不了什么。对照模型的模板不认这个参数，它的两次运行其实是同一种配置，每题只跑一次，结果却相差 3 分（29 对 26）。这就是这组测试的噪声下限，小于 3 分的差距只能算打平。本轮受时间所限没有做多次重复，这一点写明，不含糊过去。

四、终端 Agent：Mini 1/2，对照 2/2
这一组对应官方公布的 Terminal2.1 66.3 和 Automation 长程 agent 27.3 这两个方向，同样是口径不同，不能直接比分。任务：读一份冻结的 A 股日线 CSV（平安银行 000001，645 个交易日），算 MA/RSI/MACD，做双均线回测，出图与指标 JSON。判定：脚本零错退出、产物齐全、指标落在合理区间。两边都用 reasoning_effort=none，各跑两次。

这一项对照更稳，照实写。
Mini 成功的那次（results/agent/nex-mini-nothink_r2/）是标准的写代码、执行、读报错、改对。第一版脚本把 MACD 的指数平均写成了 close.ema(...)，运行报错：
AttributeError: 'Series' object has no attribute 'ema'
它读完 traceback，判断当前 pandas 不支持这个方法，自己写了一个递推的 EWMA 函数替换掉，重跑零错退出，再补一个验收脚本确认 JSON 里没有 NaN、图片非空。
那「4 次报错」要说清楚：只有上面这一次是真正的代码 traceback。另外三次是它先去运行还没写出来的文件（inspect.py、verify.py），报文件不存在，下一轮再把文件写出来。都改对了，但性质不同。
失败的那次（nex-mini-nothink_r1/）更值得看。脚本零错退出，图和 JSON 都在，自己写的验收脚本也通过了，但回测做了 37 笔交易，净值始终为 1.0，仓位没有作用到收益上。判分器最初把它判了通过，是后来修正合理区间、要求净值必须真的动过之后，才把这次判成失败。也就是说，按修正前的判分器，Mini 这一项是 2/2。1/2 是修正后的分数，我们认这个。

六、判分器抓出了 6 个自己的 bug，其中一个偏向 Mini
每个判分器先用已知正确的参考件跑一遍，必须满分才用于评测模型：看图复现 40/40，Flappy Bird 9/9，Three.js 10/10，看板的 DOM 与 canvas 两种实现各 10/10。这一步一共抓出 6 个问题：一道因审批人那一行画到了画布边界外而无法作答的题；一个用 2D 上下文读 WebGL 画布、对静态 Three.js 页面永远判通过的动画检查；看板题允许纯 DOM 实现但检查只认 canvas 或 svg；博客页因 12288 token 预算不够而两边同时调到 28672；第四节那个回测判定；以及下面这个。
第 6 个要单独说：看板页原来的检查只看源码里有没有坐标轴、三个按钮和那些数字，所以一个画图函数抛了异常、一根柱子都没画出来的页面照样拿 8/9。加上「画布上真的有数据」这项检查后，重判两边所有已保存的页面，Mini 在对应配置下少了 1 分，对照没变。六个 bug 里只有这一个在偏向被测方，改掉了。
七、边界：测了什么，没测什么
本次实测的是：文档内容识别、看图复现开发、可交互页面生成、终端 Agent 自修复、部署与吞吐。生成类题目每题只跑一次，Agent 各跑两次，噪声下限见第三节。
本次未复现的官方项目：OSWorld、OSWorld2、GDPval、Terminal-Bench 2.1、DeepSWE、Browsercomp、Toolathlon。它们各自需要专用评测环境，本文的实测分数不能与之混为一谈。厂方公布的同尺寸两代对比如下，仅作背景：

八、复现方式
原始数据在 results/doc/、results/web/、results/interactive/、results/agent/，每题都有模型原文与判分依据，模型写出的每个页面连同真实渲染截图都在对应目录下。题目生成用 scripts/make_doc_suite.py、scripts/make_doc_suite2.py、scripts/make_web_refs.py，跑一个模型全套用 scripts/run_suite.sh，重新汇总用 scripts/aggregate_nex.py。
结论
一个 35B 的开放权重模型，在同尺寸对照面前做到同水平：文档识别打平，看图复现打平，可交互页面在噪声范围内打平，终端 Agent 落后一次。文档识别和看图复现两组，它明显更省 token 和时间。厂方标的 OmniDoc 92.2 那个难度档，Mini 每一题都答对了，但同尺寸对照也全对，这套题分不出两者的高下。它多给了一个对照模型没有的控制项，但你必须知道怎么用，不知道的话第一次上手就会在长生成任务上踩坑。
