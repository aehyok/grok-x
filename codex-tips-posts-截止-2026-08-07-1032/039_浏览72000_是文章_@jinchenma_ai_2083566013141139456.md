# 如何用飞书文档实现云端AI知识库

朋友们大家好啊，我是金尘马。

有些朋友已经在用 Codex、Claude Code 这类 Agent，也想做 AI 知识库，却卡在了资料到底存哪里。

Obsidian 是一个非常受欢迎的本地知识管理软件。它基于本地文件，开放、可迁移，也很适合 Agent 操作。

但对部分刚开始接触知识库的用户来说，目录、Markdown 和多设备同步都需要学习成本。

如果平时已经在飞书里写文档，又希望手机、电脑随时访问，那么飞书文档 + 官方 Lark CLI，也可以成为一条云端知识库路线。

这篇文章只解决一件事：怎样把飞书变成 Agent 可以读取、整理和回写的云端知识库。

# 一、飞书文档知识库构成

云笔记主要解决保存、同步和搜索。AI 知识库还要能找到相关资料，理清它们的关系，并把整理结果写回文档。

一套能工作的 AI 知识库，至少有四个部分。

- 飞书知识库负责页面树和知识空间。
- 飞书文档负责保存具体内容。
- Lark CLI 负责把文档能力交给 Agent。
- Agent 加工作规则负责整理和维护。
可以把飞书理解成云端资料室，CLI 是 AI 操控云端资料室的工具，Agent 是进资料室干活的助手。

资料室搭好以后，还得给助手明确权限和规则。否则，要么资料没人整理，要么 Agent 容易改错文件。

# 二、这条路线适合谁

这套方案更适合云端优先、经常跨设备使用、已经习惯飞书，并且手里有 Agent 工具的人。

如果更看重本地开放文件、离线使用、Git 版本管理和完整迁移能力，Obsidian 或其他 Markdown 方案依然更合适。大家根据自己的情况，选择合适的方案即可。

开始前需要准备：

- 一个可以执行终端命令的 Agent。例如：WorkBuddy、Codex、Claude Code等。
- 一个飞书账号。
- 一台能够运行 Node.js 与 npx 的电脑，基本上是个 windows 和 Mac 电脑都支持。
- 创建飞书应用并完成用户授权的条件。
第一次测试只使用无敏感信息的文档。不要直接把工作机密、客户资料或唯一原件交给 Agent。

# 三、先讲清 Lark CLI 能做什么

Lark CLI 是飞书官方提供的命令行工具，也为 AI Agent 准备了对应的 Skills。

搭这套最小知识库，只会用到三组能力。

Docs 负责创建、读取和更新文档。Wiki 负责知识空间与页面节点。Drive 负责搜索文档和 Wiki。

这三组能力刚好对应知识库最常见的动作：找到资料、读取内容、创建页面、调整结构，再把整理结果写回飞书。不用背下所有命令，记住哪类任务交给哪组能力就够了。

安装和认证也可以直接交给正在使用的 Agent，不需要自己打开终端逐条执行。 把下面这段话发给它：

[link](https://x.com/jinchenma_ai)
Agent 可以代为运行命令，但填写应用信息、浏览器登录和授权确认仍可能需要自己完成。

OAuth 可以理解为给 CLI 发一张有范围的通行证。它只能操作当前身份有权访问的资源，并不是装完以后就能读取全部飞书文档。

等 Agent 返回当前登录身份和认证有效，再继续创建页面。如果没通过，就让它先检查应用配置和登录，暂时不要创建页面。

# 四、直接用 CLI 创建最小知识结构

第一版可以搭建这四个页面：

- 知识库说明
- 待整理
- 主题知识
- 项目与输出
知识库说明保存工作规则，待整理用来接收新资料，主题知识沉淀长期内容，项目与输出承接正在推进的任务。先有这四个入口，Agent 才知道新资料该放哪里，整理后应该进入哪个主题或项目。

其中最重要的是知识库说明。它相当于给 Agent 的工作守则，至少写清允许读取哪些页面、写入前必须先给方案、不能删除或覆盖原文、新页面必须保留来源链接。

把下面这段提示词交给 Agent：

[media entity 3]
确认方案没有选错知识空间，再让 Agent 执行。

```text
请只读取我指定的飞书文档，完成以下工作：

1. 列出实际读取的文档和链接；
2. 概括每篇文档的主题；
3. 找出重复内容和可以建立的关系；
4. 建议它们应该进入哪个主题或项目页面；
5. 输出拟新增、拟修改的页面清单。

禁止创建、移动、覆盖、删除或分享任何文档。
没有我的确认，不执行写入。
```

完成以后回到飞书检查四件事：节点位置是否正确，页面内容是否完整，链接能否打开，原有文档有没有被修改。

飞书界面支持文档引用关系和关系图，CLI 的文档格式也支持普通链接与 @文档。不过，目前的官方资料没有明确说明 CLI 可以直接查询完整反向引用列表。

第一版先把关系做成可点击的正向链接。

# 五、跑通第一个真实任务

知识结构建好以后，选两三篇测试文档放进待整理区。第一个任务只读，不让 Agent 动手修改。

[media entity 6]
这一步的验收标准很直接：Agent 读到了正确文档，结论能够回溯到来源，并且飞书里没有任何内容发生变化。

检查方案以后，再发送第二段指令：

```text
请帮我安装并配置官方 Lark CLI。

按顺序完成下面四步：
1. 执行 `npx @larksuite/cli@latest install`；
2. 执行 `lark-cli config init`；
3. 执行 `lark-cli auth login --recommend`；
4. 登录完成后执行 `lark-cli auth status`。

需要我填写飞书应用信息、打开浏览器登录或确认授权时，
暂停操作并提醒我接手。
最后告诉我当前登录身份和认证是否有效。
不要读取、创建或修改任何飞书文档。
```

写完以后，不要只看命令有没有报错。回到飞书检查页面位置、正文内容、来源链接和原文，再换一台设备打开同一个知识空间。这些都没有问题，第一版才算跑通。

文档里的链接或提示词也可能影响 Agent 判断，所以只要涉及重要内容，写入前都要人工确认。 格式异常时回到飞书界面验证，不把一次成功当成所有账号都能稳定复现。

# 写在最后

飞书负责云端保存和多设备访问，Lark CLI 给 Agent 一个操作入口。知识库能不能长期用下去，要看工作规则是否清楚，以及真实任务能不能反复跑通。

不要一上来就想着做全自动整理，也别一上来就无脑把所有资料都搬进去。

找几篇测试文档，让 Agent 先读、再提方案，确认后只完成一次小范围写入。这个流程稳定以后，再逐步扩大范围。

如果以后更看重本地文件和迁移自由，可以选择 Agent + Obsidian 的组合。如果更看重云端访问和飞书现成的文档体验，那这套方案会更适合你。

```text
我确认以上方案。

只执行已经批准的新增和修改：
1. 创建对应的主题页或整理报告；
2. 保留每条内容的来源文档链接；
3. 更新指定索引；
4. 不删除、不覆盖原文；
5. 完成后列出所有新增和修改的页面链接。

如果实际情况与方案不一致，立即停止并告诉我。
```
