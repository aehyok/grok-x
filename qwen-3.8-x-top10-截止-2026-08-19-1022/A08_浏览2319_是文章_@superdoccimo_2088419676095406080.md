# Qwen3.8-27B、ついに重み公開。ここからは「期待」ではなく「再現」の勝負になる

「Qwen3.8-27Bが出るらしい」

その段階は、もう終わりました。

2026年8月15日現在、Alibaba Qwenの公式Hugging FaceにはQwen3.8-27Bのモデルカードだけでなく、設定ファイル、トークナイザー、画像・動画用preprocessor、そして18分割されたsafetensorsの重みが実際に並んでいます。

リポジトリ表示は約55.6GB。ライセンスはApache-2.0です。

つまり今回の本当のニュースは、

**「27Bモデルが発表された」ことではありません。**

同じ重みを取得し、同じ設定を残し、量子化や推論基盤を変えながら、

**自分の機材と、自分の仕事で、品質と速度を比較できる段階へ進んだことです。**

Qwen3.8-27Bの評価は、期待を語るフェーズから、

**再現できるかを測るフェーズ**

へ移りました。

そして私は、ここからの方がずっと面白いと思っています。

# 前回の「予告」と、今回の「公開」はまったく違う

前回Qwen3.8-27Bを取り上げた時点では、27Bクラスのopen-weightモデルが来るという話はあっても、肝心の空欄が残っていました。

- 本当に重みが公開されるのか
- ライセンスは何か
- どんなアーキテクチャなのか
- コンテキスト長はいくつか
- thinkingはどう制御するのか
- どの推論基盤で扱えるのか
- 公式評価はどうなっているのか

現在は、そのかなりの部分を公式配布物から確認できます。

公式モデルカードでは、Qwen3.8-27Bは27Bのlanguage modelにVision Encoderを組み合わせたモデルとされ、64層の構成、Multi-Token Prediction（MTP）の訓練、画像・動画理解への対応が明記されています。

ネイティブコンテキスト長は、

**262,144 tokens**

です。

そしてRoPE scaling、具体的にはYaRNを使うことで、

**最大1,000,000 tokens**

まで拡張する方法も公式に案内されています。

さらに、公式配布ページには、

- Hugging Face Transformers
- vLLM
- SGLang
- TokenSpeed

などでの利用・配備方法が案内されています。

ここまで揃うと、ニュースの意味が変わります。

名前やベンチマークを眺めるだけではなく、

**実際に「AIにお願いする仕事」を流して比較できる。**

ここが大きい。

# 18分割の重みが本当に置かれている

今回、特に重要なのは「open-weight予定」ではなく、配布物が実体として存在していることです。

公式Hugging Faceのファイル一覧には、

model-00001-of-00018.safetensors

から

model-00018-of-00018.safetensors

まで、18個のweight shardが並んでいます。

さらに、

- config.json
- generation_config.json
- chat_template.jinja
- tokenizer.json
- preprocessor_config.json
- video_preprocessor_config.json
- model.safetensors.index.json
- crc32.txt
- LICENSE

なども確認できます。

これはかなり大切です。

「オープンモデル」と一口に言っても、

紹介ページだけがある状態と、

**重み、設定、ライセンス、前処理、chat templateまで取得できる状態**

では意味が違います。

後者なら、第三者が同じ出発点から検証できます。

# Apache-2.0になった意味

公式Hugging FaceではライセンスがApache-2.0と明記されています。

これによって、少なくとも「ライセンスが不明だから検証計画すら立てにくい」という状態からは進みました。

もちろん、

**Apache-2.0 = 何をしても考えなくていい**

ではありません。

実際の製品やサービスへ組み込むなら、ライセンス本文、依存物、利用する量子化物、周辺ソフトウェア、自社データの扱いまで確認する必要があります。

それでも、

**ローカルで評価し、自分のシステムへ組み込む可能性を具体的に検討できるようになった**

という差は大きいでしょう。

# 実は「27B」だけ見ても、このモデルの特徴は分からない

Qwen3.8-27Bは単なるテキスト用27Bモデルではありません。

公式モデルカードでは、

**Causal Language Model with Vision Encoder**

とされています。

画像と動画をネイティブに理解し、STEM図表、文書、長時間動画なども対象にするモデルとして説明されています。

さらにQwen側は、

- coding
- professional work
- research
- long-horizon agentic tasks
- environment feedbackを受けるagent execution

を今回の重点領域として挙げています。

つまり見るべきなのは、

「27Bなのに会話が賢い」

だけではありません。

**コードを書き、環境から結果を受け取り、次の操作を決め、複数ステップを進められるか。**

こちらが実運用では重要になります。

# 公式ベンチマークで目立つ「SWE-bench Pro 61.7」

公式モデルカードには多数の評価結果が掲載されています。

代表的な数字を抜き出すと、

- Terminal Bench 2.1: **73.0**
- SWE-bench Pro: **61.7**
- DeepSWE 1.1: **42.2**
- CoWorkBench: **70.7**
- IFBench: **79.5**
- GPQA Diamond: **89.2**
- LiveCodeBench v6: **90.3**

と報告されています。

マルチモーダル側でも、

- OSWorld-Verified: **84.3**
- WebArena-Verified: **64.8**
- AndroidWorld: **81.9**
- OmniDocBench 1.5: **91.1**
- RealWorldQA: **85.9**

などが掲載されています。

数字だけを見ると、かなり派手です。

しかし、ここで一度ブレーキを踏みます。

# SWE-bench Pro 61.7を、そのまま「自分の仕事の成功率61.7%」とは読めない

公式モデルカードには、評価条件についてもかなり重要な注記があります。

SWE-bench Proでは、Qwen側のモデルはClaude Code harnessを使い、temperature=1.0、top_p=0.95、256K contextで評価されています。

また、問題があると判断されたtaskを修正し、baselineモデルを再評価したと説明されています。

一方、比較表に載るOpus4.6 Maxについては、その行だけ公式報告値を利用したと明記されています。

つまり、

**表にモデル名が横一列で並んでいるからといって、すべて完全に同一条件の測定とは限りません。**

さらにQwenSWEBenchやCoWorkBenchには、Qwen側のin-house benchmarkも含まれています。

これは「数字を信用するな」という話ではありません。

むしろ逆です。

公式値は重要な情報です。

ただし用途は、

**採用決定ではなく、検証開始の判断材料**

です。

「61.7だから最強」

ではなく、

**「このモデルなら自分のコード修正セットでも試す価値がありそうだ」**

くらいに読む。

私はその距離感がちょうどいいと思っています。

# ベンチマークを見るときは、モデル名よりharnessを見る

これはQwen3.8-27Bに限った話ではありません。

AIエージェント系ベンチマークでは、

**モデルだけが仕事をしているわけではありません。**

- どのharnessを使うか
- どんなtoolを渡すか
- contextはいくつか
- timeoutはいくつか
- sampling parameterは何か
- 何回試すか
- graderは何か
- どこまで外部操作できるか

によって結果が変わります。

実際、Qwenのモデルカードでも複数の評価についてClaude Code harness、OSWorld scaffold、graderなどの条件が明記されています。

だからこれからAIエージェントの性能を見るときには、

**MODEL**

だけではなく、

**MODEL × HARNESS × TOOLS × SETTINGS × EVALUATOR**

で考えた方がいい。

これはローカルLLMを自分のagentへ組み込む場合にも、そのまま当てはまります。

# thinking modeが標準ON

Qwen3.8-27Bは、標準ではthinking modeで動作します。

そして公式に、

reasoning_effort

を使って推論の深さを調整できます。

設定は、

- xhigh：標準。複雑なタスク向け
- medium：精度と速度のバランス
- low：速度とコストを重視

の3段階です。

さらに、

preserve_thinking

も標準で有効になっています。

これはマルチターンの会話で、過去メッセージに含まれるthinking blocksを保持し、agent taskでの判断の連続性や重複推論の削減に利用する設計です。

ここまでは仕様の話。

しかし、もっと重要な一文があります。

# 「lowにすれば仕事が速く終わる」とは限らない

Qwen自身がモデルカードで注意しています。

マルチターンのagentic taskでは、reasoning effortを下げることで1ターンの応答が高速になっても、

- 分析不足
- failure増加
- retry増加

によって、

**最終的なtask completion timeやtoken consumptionが増える可能性がある**

と説明しています。

これはものすごく重要です。

LLMを比較するとき、

「何token/sec出るか」

だけを見てしまいがちです。

でもAIエージェントでは、本当に知りたいのは別です。

**仕事が終わるまで何分かかったのか。**

です。

たとえば、

Model A

1回20秒
成功率95%
retryほぼなし

Model B

1回10秒
成功率60%
何度もやり直し

なら、Bの方がtoken生成は速くても、

**仕事としては遅い**

可能性があります。

# これから見るべきは「tokens/sec」ではなく「task/sec」

少し極端に言えば、

ローカルAIエージェントでは、

**tokens per secondよりtasks per hour**

の方が重要になるかもしれません。

私は少なくとも、次を一緒に測りたいです。

- model load time
- prompt processing time
- time to first token
- generation speed
- reasoning time
- tool execution time
- retry回数
- 最終的なtask completion time
- success rate
- 人間が修正した量

そして最終的には、

**一つの仕事を終わらせるために、何秒・何token・何回の修正が必要だったか**

を見る。

ここまで測ると、reasoning_effortの意味も変わります。

# low、medium、xhighを仕事別に試す

たとえば自分のagentにQwen3.8-27Bを入れるなら、私は3設定を同じ仕事で比較します。

単純な抽出

文書から数字を拾う。

→ lowでも十分かもしれない。

記事作成

複数資料から事実と解釈を分離する。

→ mediumとxhighを比較したい。

コード修正

repositoryを読み、原因を探し、編集し、testする。

→ xhighでretryが減るなら、1ターンが遅くても総作業時間は短くなる可能性がある。

長時間agent

toolを何度も使い、途中結果から方針を修正する。

→ preserved thinkingを含めて検証したい。

つまり、

**モデルに一つの設定を固定する必要はありません。**

仕事ごとに適切な推論量を決める方が自然です。

# 262,144 tokensと1,000,000 tokensは、同じ数字ではない

ここも非常に重要です。

Qwen3.8-27Bのネイティブコンテキスト長は、

**262,144 tokens**

です。

最大1,000,000 tokensという数字は、YaRNによるRoPE scalingを使った拡張です。

公式モデルカードには、vLLM、SGLang、TokenSpeedで1M contextを利用するための具体的設定まで掲載されています。

しかし同時に警告もあります。

現在の主要open-source frameworkで使われるstatic YaRNでは、入力長にかかわらずscaling factorが固定されるため、

**短いテキストで性能へ影響する可能性がある**

とQwen自身が注意しています。

そのため、長いcontextが本当に必要な場合だけ設定変更することを推奨しています。

つまり、

**「1M対応だから最初から1Mにする」**

は雑です。

# 最大コンテキストは「常用設定」ではなく「必要時の上限」と考える

私ならこう試します。

1. 普段の入力長を測る
2. まずnative 262K以内で評価する
3. 32K、64K、128K、262Kと段階的に伸ばす
4. 品質と速度とメモリを記録する
5. 262Kを本当に超える用途だけYaRNを試す
6. 1M設定のまま短い仕事も再評価する

特にagentでは、

**巨大コンテキストを全部突っ込むこと**

と

**必要な情報を適切に取り出せること**

は別能力です。

RAG、検索、chunking、要約、workspace、memory設計で入力を絞れるなら、その方が効率的な仕事もあります。

1M contextは巨大な倉庫です。

でも倉庫が大きくなっても、

**どの棚に必要な部品があるか分からなければ仕事は速くなりません。**

# 公開直後から量子化と実機測定が始まった

open-weightモデルの面白さは、ここです。

重みが出ると、メーカーの発表だけで時間が止まりません。

すぐ第三者が触り始めます。

公開当日には、すでにcommunity GGUFや量子化版を使った実機検証が始まっています。

たとえば128GB Strix Haloでの第三者測定では、同一環境でQ5とQ8を比較し、32K contextでのprefillやgeneration速度まで公開されています。

投稿者自身も、

**これはthroughput測定であり、Qwen3.8がQwen3.6より品質面で優れているかはまだ分からない**

と明記しています。

この姿勢が大切です。

「動いた」

と

「良かった」

は違います。

さらに、

「私のPCで良かった」

と

「あなたのPCでも良い」

も違います。

# MTPも「対応している」だけでは評価できない

Qwen3.8-27Bは公式モデルカードでMTP、Multi-Token Predictionを複数stepでtrainingしていると説明されています。

公開直後のStrix Haloコミュニティでは、llama.cppでMTP speculative decodingを有効にした実測もすでに出始めています。

ある報告では、特定のQ4量子化・特定build・特定prompt条件で、MTPなしから大幅にgeneration速度が伸びた結果が共有されています。

ただし、これもそのまま一般化してはいけません。

MTPの効果は、

- hardware
- quantization
- llama.cpp build
- draft token数
- prompt
- context
- acceptance rate

によって変わります。

だから記事で書くべきなのは、

「MTPで○倍速い！」

ではなく、

**「MTPを評価対象へ追加できるようになった」**

です。

# 量子化も「何bitなら動くか」で終わらせない

Qwen3.8-27Bが公開されたことで、すでに複数のcommunity quantizationが作られています。

ある公開当日の比較では、同じマシン・同じharnessへ複数のcommunity GGUFを通し、元のBF16変換を基準として量子化誤差を比較する試みまで出ています。

ここも面白い。

量子化ではよく、

「16GBに入った」

「Q4なら動く」

という話だけになりがちです。

でも本当に知りたいのは、

**入ったあとに、仕事が壊れていないか**

です。

低bit化してVRAMに収まっても、

- tool callを壊す
- JSONを壊す
- 長文で指示を落とす
- reasoningが崩れる
- coding success rateが下がる
- retryが増える

なら、実用上は安くなっていない可能性があります。

# 同じモデルでも「量子化」は別モデルくらいのつもりで測る

私はローカルLLMを評価するとき、

**BF16 Qwen3.8-27B**

と

**Q4 Qwen3.8-27B**

を、単純に「同じモデル」と考えすぎない方がいいと思っています。

もちろん元の重みは同じです。

しかし実運用上知りたいのは、

**その配備形態で仕事が成功するか**

です。

だから、

- BF16
- FP8
- Q8
- Q6
- Q5
- Q4

を変えたら、代表タスクを同じように回す。

モデル名ではなく、

**deployment configuration**

を評価単位にする。

# ここから私ならこう検証する

大規模なベンチマーク環境がなくてもできます。

普段AIにお願いしている仕事から、

**10〜30件**

だけ選びます。

たとえば、

- コード修正
- GitHub Issue調査
- 長文資料の整理
- OSSの一次資料調査
- X記事作成
- JSON生成
- tool calling
- 画像付き文書解析

などです。

そして現在使っているモデルとQwen3.8-27Bを、同じ合格条件で比較します。

# ① まず取得物を固定する

記録するのはモデル名だけではありません。

最低限、

- Model ID
- revision / commit
- weight形式
- quantization
- 推論基盤
- 推論基盤version
- chat template
- context length
- reasoning_effort
- preserve_thinking
- sampling parameters

を残します。

Qwen公式配布にはcrc32.txtも含まれています。

つまり、

**「Qwen3.8-27Bで試した」だけでは再現記録として足りません。**

# ② 品質と速度を一緒に測る

私は次を同じ表へ入れます。

品質

- success / fail
- 人間の修正量
- 指示遵守
- hallucination
- tool call成功率
- 構造化出力成功率

時間

- load
- prefill
- first token
- generation
- tool execution
- total completion time

コスト

- input tokens
- reasoning tokens
- output tokens
- retry回数
- VRAM / RAM

こうすると、

「生成は速いけれど仕事は遅いモデル」

を見破れます。

# ③ reasoning_effortを3段階で回す

同じtaskを、

- low
- medium
- xhigh

で回す。

見るのはtoken量だけではありません。

**最終的な成功率と総作業時間**

です。

もしxhighが1回あたり2倍遅くても、retryを半分以下にできるなら、agent運用ではxhighの方が安い可能性があります。

これはQwen自身がモデルカードで警告している論点でもあります。

# ④ 失敗したtaskを捨てない

ここが一番大事です。

モデル評価で成功例だけ保存しても、あまり資産になりません。

むしろ、

- JSONが壊れた
- 指定ファイル以外を編集した
- testを実行しなかった
- 存在しない事実を補った
- toolを二重実行した
- 長文途中の条件を忘れた
- 途中でtaskを完了扱いした
- reasoning loopに入った

といった失敗を保存します。

これを、

**failure regression set**

にする。

次に、

- 新しいquant
- 新しいllama.cpp
- 新しいvLLM
- 新しいprompt
- reasoning_effort変更
- context設定変更

を試したら、同じ失敗セットを再実行する。

すると評価が「なんとなく賢い」から、

**前よりこの失敗が減った**

へ変わります。

# ⑤ 長いcontextも段階的に壊す

262Kや1Mを試すなら、

最初から巨大文書を投げて「読めました」で終わらせない。

たとえば同じ重要情報を、

- 8K
- 32K
- 64K
- 128K
- 256K

の異なる位置へ埋め込みます。

そして、

- 正確に回収できたか
- 複数条件を同時保持できたか
- 冒頭の指示を最後まで守ったか
- tool selectionへ反映できたか

を見る。

**context windowの大きさと、contextを使いこなす能力は別です。**

# ⑥ Agentでは「結果」だけでなく途中も見る

コードagentなら、

最終的にtestが通ったかだけでは弱い。

途中で、

- どのファイルを読んだか
- 何回検索したか
- どのtoolを使ったか
- 不必要な変更をしていないか
- 同じ処理を繰り返していないか
- test failureをどう扱ったか

を見る。

ローカルモデルは、自分で推論環境を持てるからこそ、

**途中の挙動まで評価資産にしやすい**

という強みがあります。

# ⑦ 人間の承認点はモデル性能と別に設計する

Qwen3.8-27Bがどれだけ性能向上していても、

モデル更新を理由に、

- 投稿
- 公開
- メール送信
- 削除
- 購入
- 課金
- 権限変更
- 本番環境変更

まで自動化する必要はありません。

AIには、

**調査、比較、候補作成、下書き、修正案、test**

までお願いする。

現実へ影響するところで人間が承認する。

モデル能力と操作権限は分ける。

これは強いモデルになるほど重要になります。

# 「ローカルだから無料」という考え方にも注意

open-weightの魅力は大きいです。

APIの呼び出し回数を気にせず、自分の環境で大量に試すこともできます。

しかし、

**ローカル = コストゼロ**

ではありません。

必要になるのは、

- GPU / unified memory
- RAM
- storage
- 電力
- model download
- serving環境
- 更新
- monitoring
- security
- backup
- evaluation

です。

さらにagentなら、失敗したときの人間の修正時間もコストです。

だからクラウドAPIとローカルLLMを比較するときも、

1M tokensあたりの単価だけではなく、

**仕事一件あたりの総コスト**

で比べた方がいい。

# ローカルLLMの本当の強みは「安さ」だけではない

私がQwen3.8-27Bで一番注目しているのは、API代が安くなる可能性だけではありません。

もっと大きいのは、

**同じ重みを固定して検証できること**

です。

クラウド型サービスでは、モデルの内部更新やサービス仕様変更が入ることがあります。

open-weightなら、

- 同じweight
- 同じrevision
- 同じruntime
- 同じprompt
- 同じ評価セット

を保存しやすい。

だから、

**再現可能なAI運用**

を作りやすい。

これはagentを長期間運用するほど効いてきます。

# 私の立ち位置

私はQwen3.8-27Bを見て、

「これが新しい最強モデルだ」

と宣言するつもりはありません。

公式ベンチマークはQwen自身が公開した値です。

公開当日の実機結果は、特定のユーザー、特定のhardware、特定のquantization、特定のruntimeで得られた結果です。

262K nativeと1M YaRN extensionも分けて考える必要があります。

そして私はまだ、自分の実運用セットでQwen3.8-27Bを検証した結果を持っているわけではありません。

だから今の結論は、

**「最強」ではなく「検証可能になった」**

です。

でも、これは小さな変化ではありません。

# 「評価できるモデル」が増えること自体に価値がある

AIの世界では、新モデルが出るたびに順位表が作られます。

しかし本当に欲しいのは、

**世界一のモデル**

でしょうか。

私なら違います。

欲しいのは、

**自分の仕事を、どこまで安心してAIにお願いできるか**

です。

コード修正なら、

「testを通した」で終わらず、余計な変更をしていないか。

調査なら、

確認済み事実と推測を分けられるか。

記事作成なら、

一次資料の数字を勝手に一般化しないか。

agentなら、

toolを正しく使い、途中で仕事を投げ出さないか。

そこを測りたい。

Qwen3.8-27Bは、その評価対象として実物が降りてきました。

# 重みの公開はゴールではない

むしろ、ここからがスタートです。

**RELEASE
↓
DOWNLOAD
↓
FIX CONDITIONS
↓
QUANTIZE
↓
BENCHMARK
↓
RUN REAL TASKS
↓
SAVE FAILURES
↓
COMPARE
↓
DECIDE WHERE TO USE**

このループを回せることが、open-weightの面白さです。

公開された瞬間に、

「勝った」

「負けた」

「最強」

と決める必要はありません。

量子化する。

実機で測る。

自分の仕事を流す。

失敗を保存する。

条件を変えてもう一度測る。

そうすれば、他人のランキングではなく、

**自分専用のAIモデル選定表**

が作れます。
