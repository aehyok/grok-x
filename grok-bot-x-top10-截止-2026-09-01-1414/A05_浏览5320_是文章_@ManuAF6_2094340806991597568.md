## 正文

我以前让 Grok Bot 干得太多。

起步后很快犯了一个错：让 Bot 什么都做。它自己定范围、在自己电脑上写代码、写记忆，有时还和另一个 Bot 重叠。设置又贵又乱。

现在简单多了：

- Grok Bot 定范围、做协调
- Cursor Cloud Agent 处理仓库工作
- 每个 Bot 拥有一份清楚的活
- 记忆有明确写入规则

最大变化是把管理和执行拆开。Grok Bot 应该管活，不该把活全干完。

仓库相关流程现在是：我跟一个 Bot 说 → Bot 定范围、准备目标/约束/完成定义 → 拉起 Cursor Cloud Agent → Cursor 改仓库 → 我审结果和 PR。Grok Bot 停在控制层，Cursor 停在实现层。这比再加 Bot 重要得多。

但 Cloud Agent 解决不了协调问题。编排者把工作笔记写进 Shared memory；专家开始重叠；两个 Bot 以为自己拥有同一步；临时上下文变成永久身份；旧状态污染新工作。我跑过一周 5 Bot 团队，编码赛道不难，难的是让每个 Bot 待在自己的道里。

三条撑住的规则：

1. **一个 Bot，一份清楚的活。** 关键不是 Bot 多，是所有权清楚。如果你发现自己在说「不是那个 Acme，是另一个」，通常该拆。
2. **把控制块放在最上面。** 长职位描述拦不住坏行为。真正重要的规则要出现在其余指令之前：不要问源里已经有答案的问题；没新东西就闭嘴；编辑或创建前先展示改动；第一次碰新源时操作者看着做一遍；限制输出；不许写日记；你只拥有一份活，不抢别人的步，不是你的就交回去，不要「帮忙」；能交给 Cursor Cloud Agent 的仓库活，不要在自己电脑里实现——你是经理。
3. **记忆是写入过滤器，不是第二颗脑子。** 不是 Bot 看见的都该进记忆。PROFILE 只写明天忘掉就会一直把活干错的稳定身份和赛道规则；LOG 是带日期的短事件；NOTE 是现在相关的临时阻塞，最终应消失，永不成为身份；SHARED 只放每个 Bot 都真需要知道的、关于操作者的稳定事实。没有编排者工作笔记、会议残渣、任务列表。Shared memory 是分离消失最快的地方。

对照真实任务登记测试后，有意思的不是 Bot 变聪明了，而是它们不再互相干扰：不打开不属于自己的会议纪要，不发明任务负责人，抽取留给会议 Bot，日程留给议程 Bot，首次摄入只用官方包，丢掉只存在于自动摘要里的行，空 transcript 就保持空。

Cursor 启动规则：目标/约束/完成定义写成 8 行以内；用 Cloud Agent 而不是在 Bot 里实现；不打开别人拥有的文件；带回 PR、改了什么、故意没动什么；所有权不清就停，不要猜。

团队建起来之后再加只读审计：只告诉你什么坏了、什么已修好、什么还开着、团队现在怎么接线。建团队吸引注意力，审计阻止腐烂。评论 audit 可要 prompt。

这些都替代不了判断。Cloud Agent 仍要审。例程仍要剪。所有权仍可能设计得很差。过早再加一个 Bot，往往制造的协调成本比它卸掉的还多。

我现在的默认：从一个 Bot 开始，给它一条清楚赛道，控制规则放最上面，仓库执行交给 Cursor，审输出，只在职责真的装不下时再拆。Cursor 已经有做仓库活的基础设施。Grok Bot 给了我上面那层有用的控制层。决定第二周还能不能活下来的，不是再来一个 Bot，而是清楚所有权、显式控制和不会泄漏的记忆。
