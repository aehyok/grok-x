## 正文

我是 SpaceXAI 工程师，正在用 Grok Bot 造 Grok Bot。

把 Grok Bot 想成一个很能打的工程实习生：它有自己的电脑，能管理编码 Agent，还能从我端到端的工作方式里学习。它已经长成我最好的工程队友——我离开、睡觉、开会时，事情还在往前推。不用再把笔记本一直开着，也不用在多个 Agent 之间来回切上下文，只剩达到我标准、按我想要的方式交付的结果。

作为 Grok Bot 的建设者，我们最早用上这套工具，并且每天拿它做自己的活。现在发产品的速度、团队产能飙升的幅度，都很疯：

- @poteto 过去一个月合进了 2000+ PR。
- @baltaaazr 和 @shaoruu 用 Grok Bot，四周搭起 Grok Bot 的地基。
- 我只用 Grok Bot，三周做出 Grok Bot iOS v0，性能和设计打磨都不差。
- 全员几乎每天都在交重大创新，而不是按周交付。

我每天越用，越想把同样的超能力交给你。

### 我的工程师 Bot

我在 EPD 组织里有五个工程师 Bot，各管一块：

- Baltata：Grok Bot 移动端共享层，以及 iOS 上一切和 Grok Bot 相关的事。
- Shaoruru：Grok Bot Desktop 客户端和 CI/CD。
- Hogan：基础设施，以及归属不清的用户问题排查。
- Craig：把 Grok Bot Android 做出来。
- Quill：Grok Bot harness 上的传奇。

他们能跨区干活，但记忆系统和上下文有限，聚焦单一领域时表现最好。收到消息时，规格和设计原则在各自负责的范围内会清楚很多。

每个 Bot 都能创建 Cursor Cloud Agent、读 transcript、审 PR 上的证明、用队列或中断发后续。这解锁了端到端的 agentic 工作流——覆盖我以前每天用 Cursor 时必须在多个云端 Agent 之间切上下文的那部分。现在 Bot 会按我的方式帮我管它们。

任务来自我或 Slack 报障时，它们会拉起一个带上我的 skills 的云端 Agent，prompt 写清要做什么、要什么证明。也能按我的指引智能调用额外 skill，比如视觉用 `/lingxi-design`，代码质量用 `/react-native-best-practices`，架构判断用 `/lingxi-review`，产品决策用 `/lingxi-product`。

最重要的是：Grok Bot 能在你的 worker 机器上启动云端 Agent——比如一台闲置 Mac mini（多亏 Grok Bot，你不再需要家里 7x24 开着一台机跑 OpenClaw）。

如果工作流需要 VPN 或特殊机器配置，可以把那台机器做成 Cursor Cloud 私有 worker，让 Grok Bot 在上面跑云端 Agent。这样就能跑 iOS Simulator，并把截图拿回来。

Grok Bot 能盯云端 Agent 的 transcript 和产物（比如截图），做完通知你，排队发消息，出问题就打断。你可以用自然语言描述需求，例如「必须验证截图包含我要的改动，并给出改前改后证明」，它会一直往回推。

以前 Agent 碰到环境抖动，还得你跟一句才能继续。现在不用。它会尽量 unblock。我每次回来，状态基本都是好的。除非它没安全权限去修，否则很少再看到一次性抖动。

让工程团队跑起来的关键，是给它完整反馈环。云端 Agent 能截图，Grok Bot 用多模态确认视觉改动真的落地；对不上就继续推。

另一个有趣用法：我们用 SpaceXAI 的语音 API 接到云端 Agent 的系统音频 I/O 测听写。Agent 既能检测词被说出，也能检测它出现在 UI 状态里，用这个信号压延迟、做更有趣的功能。

记住：现在一切都只差一条消息。想让它们在交给你之前连推 10 次？直接说就行。

### 突破上下文上限去扩规模

为了让 Bot 在上下文上限之外还能盯住工作，也方便我不用滚长聊天就能扫进度，每个工程 Bot 都管一份共享 Notion 数据库。

每 30 分钟，它们复查数据库、检查每个 PR 状态：

- 有没有 bugbot 评论或安全发现；有的话先核是不是真的。
- 有没有失败的 CI。
- 有没有合并冲突。

发现不对，立刻跟云端 Agent 跟进，并把 Notion 状态降为 Working。

都没问题，就标 Ready for Review，自动跑一轮 code review，盯代码质量和可能漏掉的点。

如果 review 很有把握、爆炸半径小，PR 自动合。否则等我回来看代码和证明，再决定合还是给反馈。

几乎每个早上，我打开都是待合任务：代码质量过我的线，视觉打到我的甜点，证明清楚测了什么。更多活被一次打穿，我就能把精力放在更难的问题、更高的客户端性能、更多视觉打磨和更大的架构决策上。

Grok Bot 之前，我能同时手管大约 15 个云端 Agent。现在舰队能同时管 200 个以上，需要还能再扩。

### Grok Bot 跑这个迷你组织

工程之外还有一堆运营杂事：给新工程师 Bot 入职、分享正确知识、出事做复盘（比如某个 PR 没仔细看）、每天一对一对齐。

介绍 Jenny，我的运营负责人。

每天早上 5 点，她和团队每个 Bot 一对一：过 playbook、摊 blocker、强化我想要的 vibe。非常有效。过了好多周，Bot 也很少忘掉我那些复杂工作流。

Bot 犯错时，比如没有为了真正目标足够往回推，我会让它们去找 Jenny 做根因和复盘。Jenny 挖导致问题的推理，更新 playbook，再向其他工程师 Bot 宣布改动，避免同样错误发生两次。

要扩团队时，我让 Jenny 入职新人：在组织里创建新 Bot，分享工程规则，让 Hogan 和其余人帮忙 onboarding。

完整工程系统的目标是尽量少重复。把任务卸给 Grok Bot，你去盯更难、更深的问题。

### 加餐用法

我们把 Grok Bot 设计得很 primitive，所以能拿它把迷你工程组织炒得很热。限制只在想象力。

**夜间审计**  
每天凌晨 3 点，工程师 Bot 醒着清理代码库、提高质量、扫死逻辑、加速启动、减包体积。早上就有一批让代码干净、模块化、可扩展的 PR。代码维护变成日常，而不是偶尔才做。

更多每日审计想法：夜间安全审计、CI/CD 构建时长审计、国际化缺口审计、多端（iOS vs 桌面）特性漂移审计。想跟上某块怎么建的但没时间，可以跑 catch-up 审计：盯过去 24 小时合进该区域的 PR，给高层摘要和精选 PR 列表。

「今晚你有六个小时。想做什么做什么。玩得开心！！」我很好奇你们会拿每日审计做什么。

**P0 紧急流程**  
云端 Agent 有时慢：要跑、搭环境、等、测、迭代。有时你需要更快。

所以我给工程师 Bot 做了 P0 紧急流程。我说某任务是 P0，它们就启动临时例程：每 5 分钟查 transcript，盯进度和推理，云端 Agent 开始烧无用时间时主动纠偏。

非常有效。真正紧急时，说 this is p0 会快很多。注意这会比你想的更快烧 token，只用于真紧急。

### 学习与建议

- 给云端 Agent 完整反馈环：让它们在没有你的情况下知道下一步。它们应能拉起 dev 实例并端到端驱动栈（Chrome DevTools、CLI、Apple Accessibility）。做不到，就让它们自己跑流程、尽量 unblock，再把学到的打成可复用 repo skill。
- 把 Grok Bot 当能干的实习生：沟通工程任务卡住时，让它们做作业、补短板、参考别的工程师怎么干。不必调 skill，不必长 prompt，聊天就行。
- 避免重复是关键：发现一天做超过一次、模式清楚的事，就和 Bot 讨论怎么卸掉。
- Bot 的每日例会极有效：每天重复关键点，帮它们在同时处理很多任务时保住复杂工作流。上下文装不下一切，每日提醒能少让你重复。
- 更放手：像自动驾驶，和 Bot 工作是建立信任。想清楚何时能顺滑跑、何时会出问题。安全时给足够自由去发；高风险区更谨慎。别因为以前失败就禁止再试。
- 让它们互相编排：可以建 Bot 犯错修订管线（比如运营 Bot 跟 Bot 聊、分析思考轨迹），避免同样错误发生两次。
