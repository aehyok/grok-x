## 正文

Lenny Rachitsky 上线一周后晒出的 Grok Bot 侧栏：Support Triage、Podcast Prep、Chief of Staff、Talent Matchmaker、Finances。那是产品该有的形状——命名聊天，当人来谈。

如果开始在里面写代码，就会烧错那块表。

Grok Bot 的发布词是岗位描述：给任务，合上电脑，它们带着完成的活回来。收件箱、CRM、供应商线程，没问题。40 轮编码循环不是这个：grep、打补丁、测试失败、再 grep。如果 Bot 在聊天里做这些，每一轮都坐在 Grok Bot 上下文里。聊天变慢，下一次提问要拖着整本日志。你先感到的就是那块表。

Lenny 的 Bot 是另一种形状：每个命名聊天一份活，它们离开再回来。招聘、收件箱、信用卡、嘉宾简报。那是把 Grok Bot 当队友。把仓库循环当 IDE，才是用错。

SuperGrok Heavy 已经把账单拆开。@XFreeze 说了不爱说的部分：Grok app、Grok Bot、Cursor 是分开的池。@benvargas 说了有用的部分：让 Grok Bot 去装 grok 和 Cursor CLI，花另外两池。

拆法：Grok Bot 是薄前门。你跟人说话。它写一张票、启动一个工人、等待、把回来的东西贴上。长活不活在那条聊天里。Heavy Grok CLI 和 Cursor CLI 跑循环。那两池吞得下一整天的 agent 活，Bot 池吞不下。Bot token 保持很小，因为 Bot 从不做循环，只写请求、带回答案。

没点名 CLI，工人就是 grok。点名 Cursor，同一张票、不同工人。一次一个工人。别为了「对比」同时开两个打同一补丁，那是两份 diff、双倍 token。

Bot 聊天里该有的是活，不是日记。点名仓库、什么坏了、约束（别重写设计）、带回来什么（改了哪些文件、测试结果、短摘要）。然后别再说话。

Bot 不打开目录，不偷看工人跑，不直播，不把补丁用更干净的词再写一遍——那是第二次实现，会漂。

等，然后贴。短请求短等；带测试的多文件修复给更长窗口。总撞长窗口，说明票写糊了。到点看工人完没完。完了就贴输出；没完就说还在等。不是状态作文。更新就是最新 CLI 输出。

一天的 agent 活属于 Cursor CLI 或 Heavy grok，不属于 Bot 转录。Bot 保持薄。循环丢给另外两池。聊天小到还能用。

## 原文

Lenny Rachitsky posted his Grok Bot sidebar a week after launch. Support Triage. Podcast Prep. Chief of Staff. Talent Matchmaker. Finances. Named chats you talk to like people.
That's the product.
It's also how you cook the wrong meter if you start writing code in there.
@lennysan, 11 Aug 2026.
Grok Bot's own launch line is the job description. Give them a task. Shut the computer. They come back with finished work. Inbox. CRM. Vendor threads. Fine.

Give them a task. They come back. Still from @bot, 11 Aug 2026. Motion: Grok Imagine 1.5.
A 40-turn coding loop is not that. It greps, patches, fails a test, greps again. If the Bot does that in-chat, every turn sits in Grok Bot context. The chat gets slower. The next ask has to drag the whole diary along. You feel that meter first.
Lenny's bots are the other shape: one job per named chat, then they go off and come back. Recruiter. Inbox. Credit cards. Guest briefs. That's Grok Bot used as a teammate. A repo loop used as an IDE is the miss.
SuperGrok Heavy already split the bill. @XFreeze said the quiet part: Grok app, Grok Bot, and Cursor are separate pools. @benvargas said the useful part: tell Grok Bot to install grok and Cursor CLI and spend the other two.
That split is the theory.
Grok Bot is the thin front door. You talk to it like a person. It writes one ticket, starts one worker, waits, and pastes what came back.
The long work does not live in that chat. Heavy Grok CLI and Cursor CLI run the loop. Those pools can swallow a day's agent work. The Bot pool cannot. Bot tokens stay small because the Bot never does the loop. It only writes the ask and carries the answer.
Grok Bot has its own bar. Don't fill it with repo loops. @XFreeze, 15 Aug 2026.
If you didn't name a CLI, the worker is grok. If you named Cursor, same ticket, different worker. One worker per ask. Don't start both on the same patch "to compare" unless they asked for a bake-off. That's two diffs and twice the tokens.
What belongs in the Bot chat is the job, not the diary. Name the repo. Name what broke. Name the constraint: don't rewrite the design. Name what to bring back: files changed, the test result, a short summary. Then stop talking.
The Bot does not open the tree. It does not peek while the worker runs. It does not live-blog. It does not rewrite the patch in cleaner words. That's a second implementation, and it will drift.
Wait, then paste.
A short look at a short ask. A longer window for a multi-file fix with tests. If you keep hitting the long end, the ticket is vague. When the wait is up, check whether the worker finished. If it did, paste the output. If it didn't, say you're still waiting. Not a status essay. Updates are the latest CLI output. That's the whole reply.
One day of agent work. It belongs on Cursor CLI, or on Heavy grok. Not in the Bot transcript. @mittalparth_, 28 Jul 2026.
That's the cut. Bot stays thin. Heavy grok and Cursor CLI do the long loop. You keep the chat small enough to stay useful.
